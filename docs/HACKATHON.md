### Phase 1 interface and bounds

`jobby_discover` adds one typed task tool, with schema/manifest/runtime parity:
`operation: inspect|confirm|search`. Inspect supplies at most eight suggestions
from exact imported role fields for occupations and affirmative fact text for
skills, using a controlled public vocabulary and reviewed terminology
equivalences. A collaborator title in a bullet cannot propose an occupation.
Explicit negation/uncertainty withholds the whole skill fact; a separate affirmative
fact can support it. These conservative lexical rules can miss valid claims and
do not resolve all semantics or infer seniority. Users select up to three
suggestions and explicitly confirm country
`Canada`, a supported location, remote-only/all-arrangements, 1–720 hours,
1–10 rows per query, 1–25 rows total per run, and lexical/newest/oldest order.
The complete setup is stored separately from eligibility and submission settings.
Legacy provisional Toronto/CAD eligibility rules are not search inputs or user
consent. Source replacement/changed bytes invalidate confirmation.

Supported city inputs are Ottawa, Toronto and London in Ontario, Vancouver in
British Columbia, and Montreal in Quebec. City inputs must include the matching
province name/code, optionally followed by Canada. They normalize to
`City, PROVINCE_CODE, Canada` for both Indeed and LinkedIn. Province/territory-wide
inputs require a Canadian province/territory name/code followed by Canada;
`Canada` remains available for country-wide search. No other cities are accepted.
This is an explicit adapter input set, not geocoding or proof that returned
postings are geographically correct. Phone/credential-shaped locations are
rejected with the shared privacy checks before persistence and again before
provider calls. Bad confirmation retains the previous valid setup; invalid stored
setup is withheld and cannot invoke the provider.

Search reuses `search.discover` → `Store.add`. Provider rows are bounded before
ingestion; duplicate rows consume the requested run budget. Indeed/LinkedIn via
the installed JobSpy contract receive the same canonical Canadian location;
`country_indeed` alone cannot constrain LinkedIn. Returned geography still needs
verification. Posting dates come from source
`date_posted`; invalid/missing dates stay unknown and sort last in either date
direction. First retained source snapshots win dedupe; later aliases do not
rewrite dates or existing status/holds. Aggregator salary stays unverified.
Structured last-run failures and shortlist membership reuse Store audit events.
Up to 100 stored shortlist results are returned in deterministic order.

The existing adapter suppresses installed JobSpy diagnostics with temporary
logger filters before pre-existing provider handlers receive raw response or
exception text. A reentrant lock serializes adapter calls; nested calls and
provider worker threads stay covered. Existing handlers/filters and logger levels
are restored on success/failure; unrelated loggers remain active. Suppression is
limited to the eagerly imported `JobSpy:` loggers during adapter execution, so
other simultaneous users of those same loggers also lose those diagnostics.
This is not a general logging framework or exhaustive provider-health check:
JobSpy can internally swallow failures and return empty results. Dependency and
propagated provider failures retain their structured sanitized outcomes.

The own-namespace API adds GET/POST `/discovery`; the existing desk uses SDK
Checkbox/Select/Input/Button components and the existing scoped query/mutation
retirement guards. The maintained SDK driver now includes synthetic discovery,
reload persistence and delayed inspect/confirm/search responses across profile,
connection and focused-owner transitions, including batched A→B→A.
